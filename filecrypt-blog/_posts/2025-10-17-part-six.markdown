# FileCrypt Reimagined - A complete C Rewrite

When we came near the end of the driver’s static analysis and reverse engineering, we decided we wanted to take a step further and try to see if we could build the driver from “source”. The source, obviously, isn’t available. In our Ghidra project, though, we have reached the point where every single function inside the driver has undergone full/partial annotation (Most have received full annotations, renames, and proper type assignments). Thus, we decided to bring our decompiled code to life.

Although the option to export the entire project or individual decompiled files exists in Ghidra, it doesn’t do much beyond dumping the code that can be viewed in the decompiler window into a file. This leaves us with a lot of code that isn’t actually valid C, for example:

`chamberPath = CONCAT88(fullPathBuffer, chamberPath._0_8_);`

All of these anomalies and fillers must be dealt with manually. Each case must be examined individually to minimize errors caused by manual code editing.
We left almost all (I want to say all, but I'm afraid my memory fails me) of the original, decompiled lines in a comment above the edited line. Moreover, each function can be compared with its original decompiled version by examining it directly in Ghidra using our exported [Ghidra project][filecrypt-export]

The solution contains seven pairs of `.c` and `.h` files, each file contains functions that have the file name as their prefix, for example,
in `stsec.c` you may find `StSecpDeriveChamberProfileKey`. This brilliant idea came from Ghidra’s automatic function groupings:

![File structure]({{ '/assets/images/solution-explorer.png' | relative_url }})

The entire “source” code can be found in the [GitHub project][filecrypt-reimagined-code].

The project does build and yield a proper .sys file, but we take exactly 0x0 responsibility, accountability, and fancier legal terms for the results of trying to run it. At the stage we left it, it won't run for certain because it misses a lot of the logging and tracing funtionallty we didn't bother to implement.

# Debugging Windows drivers

When setting up our debugging environment, we started by creating a Windows 11 virtual machine in VMware Workstation. NASA engineers of the 60s couldn’t comprehend the sheer amount of RAM things like web browsers would need to display this poorly written article on your screen, let alone draw [React Native Windows start menus][react-native-article]. The Apollo 11 mission's guidance computer had 4KB of RAM, but we decided to give our VM 12 GB of RAM with the hope that the machine’s File Explorer would take our modest offering kindly. 
But more importantly, we needed to configure a serial port for the debugger connection.

In the machine’s settings in VMware, we added a serial port configured as a named pipe. We set it to `\\.\pipe\windbg` on the host side, configured as a server that waits for an application to connect. This creates the communication channel between our host debugging machine and the target VM.

`bcdedit /debug on`

`bcdedit /dbgsettings serial debugport:1 baudrate:115200`

The debug settings configure Windows to listen for a kernel debugger on `COM1` at `115200` baud, which corresponds to our VMware serial pipe.

On our host machine, we installed the Windows SDK to get WinDbg. We configured it with matching settings to our virtual machine.

Now, with this setup, we can connect to our virtual machine using Windbg and debug the kernel, but improvements can still be made. When debugging a driver with Windbg, it is hard to make connections between the assembly and the C code of the thing we are trying to debug - the filecrupt driver. Fortunately, a plugin called [ret-sync][ret-sync-git] enables us to synchronise Windbg with Ghidra. We followed the installation guide on GitHub and went through this handy [video][ret-sync-video] (Toda le YM). By the end, we were able to debug the driver and follow its execution in Ghidra.

# Ghidra Server setup

To work on a reverse engineering project in a team, we needed to figure out a way to share our work with each other. The first thing we tried was using the tool with which we are most familiar in our daily work - Git. This turned out to be a problem, as the files generated by Ghidra do not work at all with a source control like Git, so we had to find an alternative.

Luckily for us, Ghidra comes bundled with a runnable service called Ghidra Server, which allows multiple people working on the same project to synchronize their work. Unlike Git, Ghidra Server does not have an equivalent to GitHub, so we had to host our own instance of the Ghidra Server.

Before setting up the server, we needed a place to host it. We explored several cloud platforms and ultimately chose [Kamatera][kamatera] because it offered affordable Ubuntu VMs with sufficient resources to run Ghidra Server, and came pre-installed with MSTSC remote desktop interface for ease of use.

Now all we have to do is set up the server:
1. First, git clone this [bad boy][ghidra-git] on your server
2. Make sure you've got pesky Java 17 installed (`sudo apt install openjdk-17-jdk`)
3. Build it - `./gradlew buildGhidra` and move the finished build to `/opt/ghidra`. Create a dedicated user for the server - `sudo useradd -r ghidra-server`
4. Hop into the server directory, and set up your admin account with `sudo -u ghidra-server ./svrAdmin -add <your_admin_name>`
5. To run it automatically, create a simple systemd service file that points to the ghidraSvr script. Then, enable it with `sudo systemctl enable ghidra-server && sudo systemctl start ghidra-server`. Don't forget to open port 13100 in your firewall. Once it's running, you can add team members with `./svrAdmin -add <username>`
6. Create shared projects with `./svrAdmin -create <project_name>`
7. Now your teammates can connect through their personal Ghidra by clicking on the "New Shared Project" option and typing your server's IP address
